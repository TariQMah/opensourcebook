# Open Sourcebook agent connector

Runs the person's own coding agent for Open Sourcebook's chat and Open Sourcebook's work, on their own computer (`docs/DECISIONS.md` #53). The person talks in Open Sourcebook's chat; each turn is handed to this connector, which runs their installed agent, the unmodified program signed in by them the normal way, gives it Open Sourcebook's tools and nothing else, and sends every tool call back to the engine. Open Sourcebook only launches the agent: it never reads, stores, passes on or forwards the agent's login. Open Sourcebook pays for no model call in the chat.

Local only for now: it listens on `127.0.0.1`, and it calls back only to an engine on this computer.

## What it runs

With no model named, `haiku` in a chat and `sonnet` (at `high` effort) for a piece of work (a video); a chat or video can pick `haiku`, `sonnet` or `opus` and any effort. | On this Mac: a chat turn on a real login, and a boxed turn with a stand-in model. |
| `codex` (Codex CLI) | `codex exec --json` with its own login (a ChatGPT plan or an API key, as `codex login` saved it). Its models are what `codex debug models` lists; a piece of work defaults to `high` effort. | On this Mac: a chat turn on a ChatGPT login, and a boxed turn with a stand-in model. |
| `opencode` (OpenCode) | `opencode run --format json` with the providers connected in it, or its free models without an account. Its models are what `opencode models` lists. | On this Mac: a chat turn with a stand-in model. Its free models were past their free use that day, so no turn on a real model yet. |
| `cursor` (Cursor's CLI agent) | `cursor-agent --print --output-format stream-json` with the Cursor account it is signed in with (`cursor-agent login`, or a `CURSOR_API_KEY` of the person's own). Its models are what `cursor-agent models` lists; with none named, its own default. | Not yet: written against Cursor's CLI 2026.11.19 (its published package and docs), and tested with a stand-in CLI only. |
| `antigravity` (Google's Antigravity CLI, `agy`) | `agy --input-format stream-json --output-format stream-json`. On the person's own Google sign-in it runs only once the connector has checked, on that computer, that its gate holds (below); until then it is listed as checking, or as not able to run with the reason. In the box, on a Gemini API key the person gave the connector. Each also takes an API key of the person's own instead (see "API keys"). A new agent is one adapter (`src/agents/types.ts`) registered in `src/agents/registry.ts`.

## How a turn is boxed in

Each agent is started headless for each turn:

- in a new empty directory under the system temp folder, removed when the turn ends;
- with every tool of its own off: no shell, no file reading or writing, no web. Claude Code: `--tools ""`. Codex: each of its tools is a feature turned off for the run (`-c features.shell_tool=false`, `unified_exec`, `view_image`, sub-agents, apps, plugins, hooks, …) and `web_search="disabled"`, with its read-only sandbox besides. OpenCode: an agent of Open Sourcebook's own whose rules refuse every tool except Open Sourcebook's (deny `*`, then allow `opensourcebook_*`). Antigravity: a `PreToolUse` hook in the turn's own folder (`.agents/hooks.json`) whose script answers `deny` for every tool but Open Sourcebook's, with its terminal sandbox (`--sandbox`) besides. Its documentation does not say a headless run reads that hook, so the connector checks it itself on each computer rather than assume it: the first time a turn on the sign-in is asked for, and again when `agy --version` changes, it runs one check turn in a throwaway folder with the same gate and flags, asking the agent to create `canary.txt` with its own tools and to call a harmless `probe` tool of Open Sourcebook's. It passes only if the file is not there afterwards and the gate recorded a refused call; an agent that did not try is asked once more, more firmly, and anything else (the file made, an error, a timeout, not signed in) fails closed with a plain reason. A pass is kept with its version and date in the connector's own state (`~/.opensourcebook-agent-connector/antigravity-check.json`; a folder from before the rename, `~/.re-agent-connector`, is read where it is and never moved), never in `~/.gemini`; a check that could not finish is tried again after ten minutes or when the connector restarts, and one that found the gate broken only when the connector restarts or `agy` changes version. Cursor: its tools cut down to Open Sourcebook's for the run (`--allowed-tools mcp_tool_call,get_mcp_tools_tool_call`), and settings of the turn's own that refuse its shell, the web and every file read and write besides (`Shell(*)`, `WebFetch(*)`, `Read(/**)`, …). GitHub Copilot: its own tools left off the model's list (`--excluded-tools bash,view,create,edit,web_fetch,task,skill,…`) and refused by kind besides (`--deny-tool shell`, `url`, `memory`, `read`, `write`), which no allow can undo;
- with only Open Sourcebook's MCP server and Open Sourcebook's tools allowed, and nothing asking for permission (Claude Code: `--strict-mcp-config --allowedTools mcp__opensourcebook --permission-mode dontAsk`; Codex: `approval_policy="never"`, Open Sourcebook's tools approved; OpenCode: the same rules; Antigravity: Open Sourcebook's server in the turn's own folder (`.agents/mcp_config.json`), its tools approved by the same hook (`auto_approve`); Cursor: Open Sourcebook's server from a plugin of the turn's own (`--plugin-dir`, approved with `--approve-mcps`), its tools allowed (`Mcp(opensourcebook:*)`) and approvals by that list only (`approvalMode: "allowlist"`), the folder trusted for that run only (`--trust`); GitHub Copilot: Open Sourcebook's server added for the run from a file of the turn's own (`--additional-mcp-config @…`) and allowed (`--allow-tool opensourcebook`), its built-in GitHub servers off (`--disable-builtin-mcps`), and anything it would ask about refused, as a headless run can't ask);
- with no settings files of the person's, slash commands or saved session (Claude Code: `--setting-sources "" --disable-slash-commands --no-session-persistence`; Codex: `--ignore-user-config --ignore-rules --ephemeral`; OpenCode: its settings for the turn in `OPENCODE_CONFIG_CONTENT`, no project config, a private server of its own (`--standalone`), no sharing, the session kept out of its lists (`--archived`); Antigravity: no slash commands or skills expanded (`--disable-slash-commands`); its documentation gives no way to leave the person's own settings, rules and hooks out of one run, which is why the gate is checked on each computer before it runs on their sign-in; Cursor: its settings for the turn in a folder of the turn's own (`CURSOR_CONFIG_DIR`; its login is kept elsewhere), so a model it is asked for is saved there and not in the person's; GitHub Copilot: `--no-custom-instructions` (none of the person's `AGENTS.md`, `CLAUDE.md` or `copilot-instructions.md`), no plugins found on their own (`COPILOT_PLUGIN_DIR_ONLY`), the folder not trusted (so its MCP servers and hooks are not read), no temporary folder, no update, `--no-ask-user`, and the session not synced to the person's GitHub account (`--sync-session=off`); hooks the person set up in their own `~/.copilot` still run, as no flag turns them off for one run). Open Sourcebook's system prompt replaces the agent's own where the CLI allows it (Claude Code, OpenCode); Codex gets it as developer instructions beside its own; Cursor and Antigravity take none from a caller, so Open Sourcebook's instructions open the prompt they get; GitHub Copilot gets it beside its own as a custom agent of the turn's own (`--agent`, from a folder holding only that agent, `--add-dir`);
- with the connector's environment less Open Sourcebook's own settings (`OPENSOURCEBOOK_*`, and `RE_*` as they were named before: the connector's token, any API keys).

It uses the CLI's own login as it is. The connector never reads, copies, prints or forwards a credential or token file; to say whether the agent is signed in it asks the CLI (`claude auth status`, reading only `loggedIn`; `codex login status`, reading only the exit code). OpenCode keeps that in a credential list Open Sourcebook does not read; it is shown as ready, since its free models answer without an account. Antigravity has no documented command that says it either, and keeps its login in the system keychain, which Open Sourcebook does not read, so that is left unsaid until a turn ends signed out (`authentication required`). Cursor's agent says it itself (`cursor-agent status --format json`, reading only `isAuthenticated`). GitHub Copilot is like Antigravity: it has no such command, and its credentials are the keychain's or its own files.

The prompt goes on stdin. Claude Code streams the input of a tool call while it is written (`drafts` below); Codex, OpenCode, Antigravity, Cursor and GitHub Copilot report a call only once it is made.

### API keys

The person may give the connector an API key of their own, billed to them as API use: `OPENSOURCEBOOK_ANTHROPIC_API_KEY` (Claude Code), `OPENSOURCEBOOK_OPENAI_API_KEY` (Codex) and `OPENSOURCEBOOK_GEMINI_API_KEY` (Antigravity, for the box only), in this folder's `.env`. A key does two things (Antigravity's only the second):

- When the agent is not signed in, a turn runs on the key instead (`ANTHROPIC_API_KEY` / `CODEX_API_KEY` for that one run), and Settings says so. When it is signed in, its own login is used and the key is not.
- It gives work that asks for a workspace the agent's shell and the web too, in the box (below).

### A workspace: a folder of the turn's own

A caller may ask for a **workspace** (`workspace: { path }`): a folder of its own for the turn, such as the scenes service's folder for one video, where the skills are written as files. What the agent gets there, `GET /status` says for each agent (`workspaceAccess`, and `workspaceNote` in the adapter's words), and `POST /turns` answers with it (`access`):

| | On the agent's own login | With an API key, on a Mac |
|---|---|---|
| Claude Code | `files`: its file tools only | `full`: its shell, files and web, in the box |
| Codex | none: Open Sourcebook's tools only (it reads files only through its shell) | `full` |
| OpenCode | `files`: its file tools only | (no box) |
| Antigravity | none: Open Sourcebook's tools only, once the connector's check of its gate passed | `full` (never run for real) |
| Cursor | `files`: its file tools only (not yet run for real) | (no box) |
| GitHub Copilot | `files`: its file tools only (not yet run for real) | (no box) |

#### Files only, on the agent's own login

The agent's file tools (read, write, edit, search, its to-do list) work in the folder, and nothing else of its own: no shell and no web. With no way to run a command or reach a host of its choosing, its login has no way out, so it runs on its own login as it is, and Open Sourcebook touches nothing of it.

- **Claude Code**: `--restricted` (drops every tool that runs code and WebFetch, and confines the file tools to the working directory), `--tools Read,Write,Edit,MultiEdit,Glob,Grep,LS,TodoWrite`, and settings for the turn that block file reads and writes outside the working directories besides. Where there is a box it also runs inside it, as a second wall: nothing of the person's is open but the folder, the program and the tools on its `PATH` (read only), and the places Claude Code keeps its own login and state (`~/.claude*`, the keychains, its cache), which it reaches the way it always does; nothing outside those and a temporary folder of the turn's own can be written, and the shared temporary folders and other programs' sockets are shut as in the full box below.
- **OpenCode**: its rules allow its file tools and refuse any path outside the folder (`external_directory`), and every other tool stays refused. It follows links before that check, so a folder holding a link that leads out of it is refused at the start. It runs without the box (its private server talks to itself over this computer's own address, which the box shuts), so its own rules are the only wall.
- **Cursor**: `--allowed-tools` also offers its file tools (read, edit, list, search, its to-do list), its settings for the turn allow reads and writes in the workspace and keep reads to it (`sandbox.readBoundary: "workspace"`), and its shell, the web and sub-agents stay off. It has no box here, so its own rules are the only wall. A folder holding a link that leads out of it, or a `.cursor` folder (settings, rules, hooks or MCP servers it would read as the folder's own), is refused at the start. Its `--allowed-tools` is a flag its own help hides; if a later version drops it, its turns fail rather than run with more. Not yet checked with the real program.
- **GitHub Copilot**: its file tools (`view`, `create`, `edit`, `apply_patch`, `glob`, `grep`) stay on the list and reads and writes are allowed (`--allow-tool read,write`); its path check keeps them to the working directory (and the folder holding the turn's agent), with the temporary folder taken away (`--disallow-temp-dir`); its shell, the web and sub-agents stay off. It has no box here, so its own rules are the only wall. A folder holding a link that leads out of it is refused at the start. Not yet checked with the real program.

Checked on this Mac with the real Claude Code on its own login, boxed and not (a stand-in engine, the folder in the home folder): it read a skill in `skills/` and wrote a note in the folder; reading `../`, an absolute path beside the folder, `~/.claude/settings.json`, `~/.claude.json`, a link in the folder to a file outside, `/etc/hosts`, writing to the home folder and to `../`, and searching the home folder and `~/.ssh` were all refused, and it was still signed in afterwards. OpenCode was checked the same way with a stand-in model: the folder's files open, every outside path refused, its shell and web not even offered.

#### Everything, in the box, on an API key

Where this computer has the box and the agent has an API key, the turn runs there with the agent's own tools on too (its shell, files, web; still no prompts and no settings files), and the whole agent runs inside macOS's sandbox (`src/box.ts`, through `/usr/bin/sandbox-exec`). Every process it starts, a shell command, a script, a tool it downloads, is held by the same walls:

- it reads and writes freely in the workspace;
- nothing else in the home folder can be read or written (Desktop, Documents, other projects, `~/.ssh`, mail, other apps' data), nor other drives (`/Volumes`) or `/Users/Shared`. Opened only, read only: the folders on its `PATH` themselves (`~/.npm-global/bin`, not `~/.npm-global`), the install of each program linked from there (an npm package's own folder, a Homebrew kept in the home folder) and of the agent's own program. The folders above those can be seen to exist, not what is in them, as a program resolving its real path needs. Never opened for a tool: the personal folders (Desktop, Documents, Downloads, Library, …) and the ones that hold logins (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config`, …);
- outside the home folder the system can be read (`/System`, `/usr`, `/bin`, `/opt`, `/Library`, `/Applications`, `/etc`), so programs run, but not written, except devices (`/dev/null`, a terminal);
- the shared temporary folders are shut for reading and writing: `/private/tmp` (`/tmp`), `/private/var/folders` (`/var/folders`, where every app's per-user temporary and cache files sit) and `/private/var/tmp`, as other programs keep files and sockets there. The agent gets a temporary folder of its own instead, made fresh for each turn (0700, in this user's temporary folder) and removed when the turn ends, as its `TMPDIR` (and `TMP`, `TEMP`, and `CLAUDE_CODE_TMPDIR` for Claude Code). A program that ignores `TMPDIR` and writes in `/tmp` itself fails there, and so does the Mac's bare `mktemp` (it uses the system's per-user folder); `mktemp "$TMPDIR/x.XXXXXX"` works;
- it can connect to no Unix socket on this computer (an ssh agent's, Docker's, another tool's), except the system's name lookup (`/private/var/run/mDNSResponder`), without which no web address resolves;
- it can reach the web, but nothing on this computer's own address except this connector's port, which serves its turn. (The sandbox can't tell other machines on the local network apart from the web.)

The workspace must be an existing folder at least two levels inside the home folder or inside this user's temporary folder or `/private/tmp`, by its real path, and never in `~/Library` or inside an agent's, a tool's or a login's own folder at any depth (`.ssh`, `.gnupg`, `.aws`, `.config`, `.claude`, `.codex`, `.gemini`, `.cursor`, `.docker`, `.kube` and the like, a project's `.claude` too). Nor in any other dot folder at the top of the home folder (`~/.npm`, `~/.local`, any of them: where tools keep settings and logins), except inside one of the folders this connector was set up with in its own environment, `OPENSOURCEBOOK_CONNECTOR_SCENES_ROOTS`, never by a request: an installed copy lives in `~/.opensourcebook`, so its video maker works in `~/.opensourcebook/app/services/scenes/.data/<job>/work`. A dot folder deeper inside a project is fine (a clone's video maker works in `services/scenes/.data/<job>/work`). A refused folder is answered with the reason. It is kept when the turn ends; it belongs to the caller.

#### The box never uses a subscription login

In the box the agent has a shell and the web, so whatever it can read it could send out. So it never runs on your subscription login there, and can't reach it: your keychains (`~/Library/Keychains`), `~/.claude/.credentials.json`, `~/.claude.json` and `~/.codex/auth.json` are shut whatever else is open, and the agent keeps its settings in a folder of its own in the temporary folder (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`; Antigravity: a home folder of the turn's own, `HOME`, with `~/.gemini` shut besides). The providers' terms also forbid storing a subscription login, passing it on, or routing calls through it, so Open Sourcebook never does any of that (`docs/DECISIONS.md` #68).

It runs on the API key you gave the connector, and never holds even that. Its model calls go to this connector (Claude Code: `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>/model/<turn>` with the turn's secret as a gateway token; Codex: a provider of its own pointed at `/model/<turn>/v1`; Antigravity: the Gemini API called directly, `modelProvider: "gemini"` in its settings for the turn, `GOOGLE_GEMINI_BASE_URL` pointed at `/model/<turn>` and the turn's secret as its `GEMINI_API_KEY`, which the connector reads from `x-goog-api-key`), signed with a secret of that turn's own, and the connector forwards them with the key in place of the secret (`src/model-proxy.ts`), dropping whatever credential the agent put on them. Only model calls are forwarded (Claude Code: `POST /v1/messages`, `/v1/messages/count_tokens`; Codex: `POST /v1/responses`, `GET /v1/models`; Antigravity: the Gemini API's `POST /v1beta/models/<model>:generateContent`, `:streamGenerateContent`, `:countTokens` and `GET /v1beta/models`), only from this computer, and only while the turn runs; the turn's secret opens nothing once it ends. So a command the agent runs can't read the key, and the most it could leak is a secret that works only on this computer for the rest of its turn. The boxed agent's environment is otherwise only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `TERM`, and its own `TMPDIR`, `TMP`, `TEMP`.

Without a key `GET /status` says why it doesn't get everything (`workspaceUnavailable`), and the turn gets files only where its adapter can (`filesOnly`), else Open Sourcebook's tools only. Where there is no box (anything but macOS) the same holds, with the agent's own rules as the only wall of a files-only folder. `OPENSOURCEBOOK_AGENT_WORKSPACE=off` gives no turn a workspace at all.

#### Reading beside the folder, read only

A caller may also name what the agent may read beside its folder (`workspace: { path, read: [paths] }`): the scenes service names a video's `README.md`, `sources/` and `extracted/`, which sit in the job folder around `work/` (`docs/JOB-FOLDER.md`). Each path must be absolute and inside the folder that holds the workspace, and that folder must itself be one a workspace could be (for the scenes service's token, inside its own folders and never one of them itself); anything else is refused, and a named path that is not there is left out. A link in what is named (a source's link to the person's original) opens the one file it leads to, never the folder that holds it, a link to a folder opens nothing, and a file where programs keep settings, logins or keys (a dot folder at the top of the home folder, `.ssh`, `.claude`, `.codex` and the like at any depth, the keychains) is never opened. Nothing is copied.

The connector works this out once for every agent (`reachOf` in `src/box.ts`) as a plain list, `{ write, folders, files }` by real paths, and hands it to the turn (`TurnSpec.workspace.reach`). On a Mac the box opens exactly those folders and files to reading, for every agent alike (`withReach`), and writes stay in the workspace. That list is also what a sandbox on Linux or Windows is meant to take; there is none yet, so there no turn is given anything beside its folder.

| | Beside its folder |
|---|---|
| Claude Code, files only or in the box | read only, inside the box. Its own rules open folders only and follow links, so they open the folder of each file too (`--add-dir`) with every edit there refused; the box holds reads to exactly the files and writes to the workspace |
| Codex, Antigravity, in the box | read only: the box is the wall, their own sandbox and approvals are off there |
| OpenCode, Cursor, GitHub Copilot | nothing: they run without the box, and their own rules can't open a single file read only without opening it to writes or opening its whole folder |

`GET /status` says it for each agent (`workspaceReads`), and `POST /turns` answers `read: true` when it was given.

Checked on this Mac with the real Claude Code on its own login, files only and boxed, in a job-like folder in the temporary folder: it read `../README.md`, `../extracted/s1/text.md` and a source's original through `../sources/`, and was refused another file beside that original and writing `../escape.txt`; it wrote in its folder. A stand-in model asked the real Claude Code, files only and in the full box, for the same and for writing the original through its link, `../extracted/` and the job folder's own files: each refused (`test/box-run.test.ts` does the same with a shell in the box).

#### Checking the box on a Mac

`npm run check-box` runs a set of commands inside the very box a boxed Claude Code turn gets and prints which ones the walls let through (the workspace, the web and the connector open; your login, keychains, home folder, other local ports and system writes shut). Then it runs one real boxed turn of the real Claude Code through a connector started there, with a stand-in engine: the agent runs a few commands with its own shell and replies with their exit codes. Its model calls go through the connector to Anthropic with `OPENSOURCEBOOK_ANTHROPIC_API_KEY` when that is set, and otherwise to a stand-in model in the script that asks for those commands and the reply, so everything but the model itself is real, with no key and no login. It prints exit codes and names only, never a key or a file's contents.

#### Antigravity, from its documentation only

`src/agents/antigravity.ts` was written from Google's pages (antigravity.google/docs: the CLI's headless mode, reference, permissions, settings, hooks, MCP, sandbox, install and models pages, read Nov 23, 2026). No real `agy` has run against it; every part below is untried.

- **On the person's own sign-in** (a chat turn) it does not run. The documentation gives no settings file, folder or variable of a run's own, and the person's `~/.gemini/antigravity-cli/settings.json` is theirs and never written. What is built is the closest way it gives: Open Sourcebook's MCP server in the turn's own folder (`.agents/mcp_config.json`) and a `PreToolUse` hook there (`.agents/hooks.json`) whose script answers `deny`, which the documentation calls a hard block, for every tool but Open Sourcebook's (`call_mcp_tool` naming Open Sourcebook's server, or `mcp_opensourcebook_<tool>`) and `auto_approve` for Open Sourcebook's, with its terminal sandbox (`--sandbox`, commands without the network) besides. The documentation does not say that a headless run reads a folder's hooks in a folder it was never told to trust, nor how a hook's deny is weighed against the person's own allow rules or hooks; if the hook were not read, its shell would run loose on their login (`agy -p` starts in `auto` mode). Its other way, `agy acp`, asks the client about each action, but the person's own allow rules still apply without asking. So such a turn is refused and `GET /status` says it can't run yet, until it has been tried on a real install.
- **In the box**, on `OPENSOURCEBOOK_GEMINI_API_KEY`: its home folder for the turn (`HOME`) holds its settings (`modelProvider: "gemini"`, its own terminal sandbox off) and Open Sourcebook's MCP server (`~/.gemini/config/mcp_config.json`), and every tool is approved (`--dangerously-skip-permissions`), there only. That `agy` reads its settings from `HOME`, and that it sends the key as `x-goog-api-key` to `GOOGLE_GEMINI_BASE_URL`, are not documented; if either is not so, the turn fails, with nothing of the person's opened and no key in the box. Which models a Gemini API key offers is not documented either.
- Its stream-json events (`init`, `step_update`, `result` with `status`, `response`, `error`, `usage`) and `agy models` (a slug and a name on each line) are read as the headless page shows them.

Open Sourcebook's tools come from the engine with each turn (`engine/src/chat/agent/default-tools.ts`); the connector serves them as an MCP server at `/mcp/<turnId>`, guarded by a secret only that turn's agent has, and forwards each call to the engine with the turn's own token. It does not know any tool by name.

## Run it

To run all of Open Sourcebook at once, run `npm start` at the repo root (`docs/DEVELOPING.md`): it starts this connector with the others, with the shared secrets and ports filled in. What follows is for working on it alone.

Node 24 or newer (it runs the TypeScript directly).

```sh
cd services/agent-connector
npm install
OPENSOURCEBOOK_CONNECTOR_TOKEN=<a long random string> npm start
```

Settings can also go in this folder's `.env` (git-ignored; see `.env.example`), which `npm start` reads.

Then in `engine/.dev.vars` (see `engine/.dev.vars.example`):

```
CHAT_AGENT_URL=http://127.0.0.1:8650
CHAT_AGENT_TOKEN=<the same string>
```

and restart `wrangler dev`. The engine logs once that chat turns go to your agent.

A setting written under its name from before the rename (`RE_CONNECTOR_TOKEN`, `RE_ANTHROPIC_API_KEY`, `RE_AGENT`, any `RE_...`) is still read, as `OPENSOURCEBOOK_...`; the new name wins when both are set.

| Setting | Default | |
|---|---|---|
| `OPENSOURCEBOOK_CONNECTOR_TOKEN` | (required) | What the engine sends as `Authorization: Bearer`. At least 16 characters. |
| `OPENSOURCEBOOK_CONNECTOR_SCENES_TOKEN` | (none) | A second, narrower token for the scenes service, same header, at least 16 characters and not the main one. It reaches only `GET /status`, `POST /turns` with a work folder inside `OPENSOURCEBOOK_CONNECTOR_SCENES_ROOTS` (or none), and `GET /turns/:id` and `POST /turns/:id/stop` of the turns it started; anything else is 403. |
| `OPENSOURCEBOOK_CONNECTOR_SCENES_ROOTS` | (none) | The scenes service's own folders, absolute paths separated by `:` (the system's path delimiter), compared by their real paths; a work folder must be inside one of them, never one itself. Empty: its turns get no work folder. |

## Routes

| Route | Who | |
|---|---|---|
| `GET /status[?fresh=1]` | engine | `{ agent?, model?, effort?, agents: [{ id, label, installed, version?, signedIn?, apiKey?, note?, unavailable?, mark?, models?, makers?, defaultModels?, defaultEfforts?, replacesWorkPrompt?, efforts?, signIn?, install?, workspace, workspaceAccess?, workspaceNote?, workspaceUnavailable?, workspaceReads?, limit? }], running }`, kept for 30 seconds unless `fresh=1` asks each agent again (`limit` is always as it is now); `defaultModels` is `{ chat?, work? }` and `defaultEfforts` is `{ chat?, work? }`, the model and effort its adapter runs on when a turn of that kind names none (none: its own default), `replacesWorkPrompt` says whether work turns can safely replace its built-in instructions when `keepAgentPrompt` is false, and the top-level `model` and `effort` are what a chat turn of the default agent runs on then; `mark` is the agent's logo and `makers` the logos of its models' makers, each `{ path, color? }`, one filled path in a 24×24 box in that colour or the text's (`src/agents/marks.ts`), `makers` as `{ <maker>: { label, mark } }`; `models` is `[{ id, label, maker?, tier? }]` (`tier`: `"fast" \| "balanced" \| "strong"` when declared, omitted on `"auto"`) and `efforts` is `[{ id, label, weight? }]` (`weight`: `"light" \| "medium" \| "high" \| "max"`, lightest first; empty when it takes none; OpenCode's `provider/model` names come as `provider__model`); `apiKey`: it is not signed in and answers with the API key the person gave the connector; `note`: how it answers, in one plain sentence, when that is worth saying; `signIn` is the command that signs in to it on this computer, and `install` is `{ command?, url }`, its own install page and the one-line install command that page gives (each shown in Open Sourcebook's "How to connect", never run by the connector); `workspace`: that agent can get a workspace here; `workspaceAccess`: which (`files` or `full`); `workspaceNote`: that in the adapter's words; `workspaceUnavailable`: why it doesn't get everything, when the box is here but the agent isn't ready for it; `workspaceReads`: what a caller names beside its workspace is opened to it read only (see "Reading beside the folder"); `limit`: the usage limit it last ran into (see "Usage limits") |
| `POST /turns` | engine, scenes service | `{ turnId, systemPrompt, prompt, tools, callback: { url, token }, agent?, model?, effort?, kind?, timeoutMs?, keepAgentPrompt?, instructions?, drafts?, workspace?: { path, read? }, target?: { type?, id? } }` → `202 { ok, agent, model?, effort?, workspace, access?, read? }` (the agent it runs, the resolved model and effort when set, whether it got the workspace, and which: `files` or `full`, and `read` when what `workspace.read` names beside it was opened read only). `kind` is `chat` (the default) or `work` (a long piece of work, such as a video): with no `model` or `effort`, it picks the adapter's `defaultModels` / `defaultEfforts` for that kind. `target` names what the turn is for (`{ type, id }`) for the usage log. A problem it can tell at once is `{ problem, message }`; while the agent's limit has a reset time still ahead the turn is not started: `429 { problem: "agentLimit", message, limit }`. |
| `POST /turns/:id/stop` | engine | Stops the agent; the end is reported as `stopped`. |
| `POST /agents/:id/probe` | engine | Whether that agent answers now: `200 { ok: true }` or `{ ok: false, problem, limit? }`; `404` for an agent the connector does not have. See "Usage limits". |
| `GET /usage[?limit=&before=]` | engine | The finished turns in the usage log (`OPENSOURCEBOOK_USAGE_LOG`), newest first: `{ turns: [{ line, time, turnId, agent, type?, targetId?, model?, effort?, inputTokens?, outputTokens?, cacheReadTokens?, cacheWriteTokens?, durationMs, toolCalls, outcome }], next?, off? }`. Never the reported cost: no screen shows money. `limit` is 1 to 500 (50 when not given); `next`, when older turns follow, is the `before` that pages back to them (`line` is the turn's line in the log, from 1). A log not written yet has no turns, a line that is not a turn is passed over, and `off: true` says the log is turned off. Only the connector's own token reads it. |
| `POST /mcp/:turnId` | that turn's agent | MCP over HTTP: `initialize`, `tools/list`, `tools/call`, `ping`. |

- `timeoutMs`: how long the turn may run, 3 minutes when not given, never more than 45 minutes; `0` for no limit, so the turn runs until the agent ends or the caller stops it. The chat asks for at most 10 (the engine caps it); the scenes service asks for no limit while the agent makes a video.
- `keepAgentPrompt`: `true` adds `systemPrompt` to the agent's own instructions (Claude Code's `--append-system-prompt-file`) instead of replacing them (`--system-prompt-file`); Claude Code also runs with `ENABLE_TOOL_SEARCH=false`. Codex always gets it as developer instructions beside its own; OpenCode gets it as an instructions file beside its own.
- `instructions`: what the agent is told about the tools when it connects. The chat's line ("end the turn with the reply tool") when not given.
- `drafts`: names of the turn's tools whose input the caller wants while the agent is still writing it (the chat asks for `reply`, so a reply shows as it is written). The adapter reads the agent's partial tool input where its CLI streams it (Claude Code runs with `--include-partial-messages` then; Codex and OpenCode don't stream it, so they send none) and the connector posts the newest of it, at most every 250 ms, to `<callback.url>/draft` as `{ tool, input, calls }`: `input` is the JSON written so far, unfinished, and `calls` the number of tool calls before it, so the caller can tell a draft that arrives after its call. Best effort: a draft that is lost is replaced by the next, and by the call itself.

A tool call is posted to `<callback.url>/tools` as `{ name, arguments }` with the turn's token, and has two minutes to answer `{ text, isError?, images? }`. `images` is a list of `{ mimeType, dataBase64 }` (PNG, JPEG, WebP or GIF, at most 8 per call); the agent gets them as MCP image blocks after the text, and sees them. This was checked with Claude Code 2.1.325: a tool answered with a picture of a random word and the agent named the word. Anything else in `images` is dropped.

When the agent ends, the connector posts `{ outcome, problem?, limit?, text?, said?, model?, effort?, tokensIn?, firstTokensIn?, tokensOut?, toolCalls, durationMs }` to `<callback.url>/finish`. `said` is the agent's own words on why its turn failed, from its own error event (never its log), when it ended with an error itself, for the caller to show the person; `firstTokensIn` is the input tokens on the turn's first model call when the adapter reports it; `toolCalls` is how many of the caller's tools it called, so a turn that failed before any work can be told from one cut off midway. `problem` is one of `agentMissing`, `agentSignedOut`, `agentLimit`, `timedOut`, `stopped`, `error`. With `agentLimit`, `limit` is `{ resetsAt?, resets? }` when the agent said when its limit resets.

## Usage limits

When the person's agent runs out of its plan's usage, the turn ends as `agentLimit`, and the connector keeps what the agent said about when it can answer again (`src/agents/limit.ts`), never a guess: `resetsAt`, an exact time as ISO 8601 (Claude Code's refused `rate_limit_event` with its `resetsAt`, an epoch after its older error text, or a delay such as "try again in 2 hours"), and `resets`, the agent's own short words for when ("3pm (Europe/Berlin)", "in 2 hours"). A clock time without a date stays words, since only the agent knows its time zone.

The connector remembers each agent's limit in memory as `limit: { since, resetsAt?, resets? }` until a later turn of that agent ends well or a known `resetsAt` passes, and `GET /status` shows it on that agent. While a `resetsAt` is still ahead, `POST /turns` for that agent answers `429` at once without starting it; without one the turn is tried, as a refused turn costs nothing.

`POST /agents/:id/probe` checks whether the agent answers now with the smallest turn there is: an empty folder, a one-line prompt ("Reply with the single word ok."), none of Open Sourcebook's tools, the agent's own default model, at most 90 seconds. It answers `{ ok: true }` (and forgets the limit) or `{ ok: false, problem, limit? }` (remembering a limit when that is why). While a known `resetsAt` is ahead it runs nothing and answers `{ ok: false, problem: "agentLimit", limit }`. One check per agent runs at a time; a second request gets the same answer.
